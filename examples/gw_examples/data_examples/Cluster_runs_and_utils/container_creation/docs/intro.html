Concept 01

Apptainer

Apptainer is a container platform designed for scientific and high-performance computing. It provides a controlled user-space environment without requiring Bilby and all of its dependencies to be installed separately at every computing site.

  • A definition file is a recipe; in this repository that recipe is image.def.
  • The normal output is a read-only Singularity Image Format file, or .sif.
  • The process normally keeps the caller’s user identity, which suits shared clusters.
  • The container shares the host’s Linux kernel; it is not a complete virtual machine.
make publish BILBY_BRANCH=feature/bilby BILBY_PIPE_BRANCH=feature/bilby-pipe
Distinction from a virtual machine

A VM includes its own kernel. An Apptainer image supplies the user environment but relies on a Linux host kernel.

Concept 02

The IGWN Pool

The International Gravitational-Wave Observatory Network Pool is a distributed collection of computing resources. It is presented through HTCondor as a common high-throughput computing pool, even though its machines are hosted at multiple institutions.

  • An access point accepts the job submission.
  • HTCondor matches the job’s requested CPUs, memory, disk, and other requirements to an available resource.
  • An execution point runs the job, potentially at a different institution.
  • Input files travel to the execution point and requested outputs return after execution.
Distributed resources

The pool is an aggregation of resources. Two jobs from the same workflow may run at different sites, so they cannot assume a site-specific Bilby installation or shared local filesystem.

Concept 03

OSDF

The Open Science Data Federation is a distributed data-delivery system. It exposes files through a global namespace and uses geographically distributed caches to avoid repeatedly transferring the same large object from its authoritative source.

  • An origin connects authoritative storage to the federation.
  • A cache holds temporary copies closer to consumers.
  • On CIT, a direct copy is attempted first; Pelican is the fallback if the staging filesystem is not writable.
  • Outside CIT, Pelican uploads the object using a scoped SciToken.

See the OSDF staging guide for the supported upload and job-access workflow.

make publish # on CIT
make publish CIT=false # outside CIT
Data federation rather than shared storage

The OSDF URL names an object in a federation. A job may receive it from a nearby cache rather than directly from the origin where it was published.

Workflow

Bilby job lifecycle

  1. Describe the environment

    image.def starts from Ubuntu and installs Miniconda, the selected Bilby and bilby-pipe sources, bilby_tgr, and PESummary. Both refs default to sine_gaussians_addition and can be overridden with BILBY_BRANCH and BILBY_PIPE_BRANCH.

  2. Build a SIF image

    Apptainer executes the definition and creates one portable image containing the required user-space software.

  3. Give the build a distinct name

    The Makefile combines both package versions with a seconds-resolution UTC timestamp. Branch builds also include the first 12 characters of each exact installed commit, giving bilby-<version>-<commit>-bilby_pipe-<version>-<commit>-<timestamp>.sif; a release-tag component omits its commit.

  4. Publish the image

    On CIT, the image is copied directly to the user’s local OSDF staging directory. If that fails, or when CIT=false is selected, a scoped SciToken and Pelican publish the same built image remotely. The URL is recorded under the selected Bilby branch in container_images.json.

  5. Submit the job

    The launcher detects the current Git branch, reads its OSDF URL from container_images.json, and writes that URL as container_image in the HTCondor description.

  6. Stage, execute, return

    HTCondor selects an execution point, obtains the image through OSDF, starts Bilby inside Apptainer, and transfers the declared outputs.

Diagnostic note

apptainer: No such file or directory

Make found the correct build rule, but the shell could not find an apptainer executable. On macOS, installing a command alone is insufficient because Apptainer requires Linux kernel facilities. Build on a suitable Linux host, or run Apptainer inside a Linux VM such as Lima. For an image intended for common x86-64 execution sites, an x86-64 Linux build host is the least surprising choice.
